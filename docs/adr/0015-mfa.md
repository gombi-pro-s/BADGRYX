# ADR 0015: Multi-factor authentication — Supabase Auth's own MFA API, and where step-up is actually enforced

## Status

Accepted.

## Context

`RELEASE_CHECKLIST.md` had flagged MFA as a real, unaddressed gap since
early in the project. Unlike almost every other feature built this
session, MFA needed **no new schema, no new migration, and no new RLS
policy** — Supabase Auth (GoTrue) already owns factor enrollment,
challenge, and verification state entirely on its own side
(`supabase.auth.mfa.*`), the same way it already owns password hashing
and session tokens. The only genuinely new design question was: enrolling
a factor is easy to build as a UI feature, but *enforcing* it — making a
password-only session actually insufficient to reach a protected page —
is a separate, easy-to-skip step. A "MFA" feature that only lets you
enroll a factor but never actually requires it at login isn't MFA, it's a
QR code generator.

## Decision

Three real enforcement points, mirroring the existing "middleware is
UX-only, the server call is the real check" pattern already documented at
the top of `lib/supabase/middleware.ts`:

1. **`requireUser()`** (`lib/auth/session.ts`) — the one function nearly
   every protected Server Component/Action/Route Handler in this app
   already calls. It now also calls
   `supabase.auth.mfa.getAuthenticatorAssuranceLevel()` and redirects to
   `/login/verify-mfa` if the session's `currentLevel` hasn't reached the
   `nextLevel` the account's verified factors require. This is the real
   check — every other protected surface inherits it for free because
   they already call `requireUser()`, the same way they already inherit
   RLS enforcement for free by using the caller's own Supabase client.
2. **`middleware.ts`** — the same check, mirrored, so a browser gets
   redirected before a protected page even renders rather than after.
   Explicitly documented as *not* a substitute for #1, exactly like the
   existing unauthenticated-visitor redirect it sits next to.
3. **`signInAction()`** — after a successful password check, checks AAL
   and redirects to `/login/verify-mfa?next=...` instead of `next`
   directly, so a user with MFA enrolled sees the step-up prompt
   immediately rather than landing on a page that then bounces them.

`getAuthenticatorAssuranceLevel()` with no `jwt` argument reads the
current session and, per the SDK's own documentation, "rarely uses the
network" — this is not an expensive call to make on every protected
request, unlike e.g. `admin_search_users()` or other real Postgres round
trips already made per-request elsewhere in this app.

`/login/verify-mfa` is a new route, deliberately outside `requireUser()`'s
own gate (it calls `getCurrentUser()` directly instead) — it needs to be
reachable by exactly the population `requireUser()` would otherwise
redirect: signed in at `aal1`, not yet at `aal2`. Reaching it without any
session at all still redirects to `/login`, same as everywhere else.

`/settings/security` is the enrollment UI: start enrollment
(`supabase.auth.mfa.enroll({factorType: 'totp'})`, which returns a QR
code + manual-entry secret), verify a 6-digit code
(`challengeAndVerify()`) to activate it, list currently verified factors,
and remove one. Starting a fresh enrollment first cleans up any
previously abandoned (never-verified) factor for that user — otherwise a
scan-didn't-work-tried-again pattern would silently accumulate orphaned
unverified factors with no way for the user to see or clear them.

## Why

Building the enrollment UI first and asking "does this actually get
enforced anywhere?" is exactly the question that would have otherwise
gone unasked until manual testing (which itself isn't possible in this
sandbox — see Consequences). Choosing `requireUser()` as the enforcement
point, rather than inventing a new wrapper or a new middleware-only check,
follows the same reasoning as every prior "where does this get enforced"
decision in this app: the answer is always the point every protected
surface already funnels through, not a new parallel mechanism a future
page could forget to call.

## Consequences

- No SQL migration and no SQL regression test exist for this phase —
  there is genuinely no Postgres surface to test; MFA state lives
  entirely in `auth.mfa_factors`, a table this schema doesn't own or
  touch. This is a first in this session (every other phase added at
  least one migration) and is called out explicitly rather than silently
  having "0 new SQL assertions" look like an oversight.
- Like every other Supabase Auth-dependent code path in this sandbox
  (`signUpAction`, `signInAction`, password reset), this cannot be
  click-tested end-to-end here — there's no real Supabase project to
  authenticate against. Verified instead by `tsc --noEmit`, ESLint, a
  clean production build (including the two new routes,
  `/login/verify-mfa` and `/settings/security`), and an e2e test
  confirming `/login/verify-mfa` sits behind the same "no session → back
  to /login" wall as everything else.
- A real Supabase project may need TOTP explicitly enabled under Auth →
  Multi-Factor Authentication in the dashboard before `enroll()` succeeds
  — noted in `MANUAL_SETUP.md`, not assumed to be on by default.
